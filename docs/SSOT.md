# SSOT: One Fact, One Owner

> Every fact has exactly one owner. Consumers derive from it, or a generator produces their copy, or a build check fails when they drift. If you are about to write a value, type, formula, list, color, path, or number that already exists somewhere, **stop and use the owner**. If there is no owner, **create one owner**, in the right layer, and register it here.
>
> Creating a second mechanism for something that already has an owner is a defect, even if it "works", even if it is faster, even if it is temporary.

## Decision procedure (follow in order)

1. **Search first.** Grep for the concept (`rg -n "<concept>"`), check the register below, check `reps/vocab.py`, `constants.json`, `design/tokens.css`, `routes.ts`, `generated/`. If an owner exists, use it.
2. **Can it be derived?** If it can be computed from existing facts, compute it on read. Do not store it. (`set_muscle` is a view over `lift_muscle`, not a table.)
3. **Pick the owning layer** by the nature of the fact:

| Kind of fact                                                    | Owner                                                                                |
| --------------------------------------------------------------- | ------------------------------------------------------------------------------------ |
| A recorded fact about the user's training                       | SQLite table + Pydantic model                                                        |
| A relationship that must always hold                            | Foreign key / `CHECK` / `UNIQUE`                                                     |
| A tunable number or taxonomy                                    | `constants.json` (validated by `ConstantsModel`)                                     |
| A closed set of names (status, verdict, tier)                   | `reps/vocab.py` `StrEnum`                                                            |
| A domain computation (e1RM, PR, stall, week bucket, slot match) | One function in `reps/`, in the module named in the register                         |
| A shape crossing Python/TS/Worker                               | Pydantic model in `reps/models.py`; everything else is generated by `scripts/gen.py` |
| A color, font, radius                                           | `dashboard/src/design/tokens.css`                                                    |
| An icon                                                         | `dashboard/src/design/icons.ts`                                                      |
| A URL/route                                                     | `dashboard/src/routes.ts`                                                            |
| A chart's padding/plot area                                     | That chart's `layoutOf`, consumed via the returned `HitMap`                          |
| A number quoted in docs                                         | A doc marker filled from `constants.json`                                            |
| A test dataset                                                  | `tests/scenarios.py` (generated into TS fixtures)                                    |
| A tool name referenced from code or docs                        | The MCP registry; referenced through `Fix(tool=...)` or lint-checked backticks       |

4. **Add it to the register** in this file (concept, owner, mechanism, tier, gate). A change that adds an owner without a register row is incomplete.
5. **Second mechanism?** Only if it passes every question below. Record the answer in the register's "sanctioned duplication" section. If any answer is "no", do not do it.
   - Does a runtime or language boundary make deriving/generating impossible (not merely inconvenient)?
   - Is there a mechanism (generator, parity test, grep gate) that fails the build on drift?
   - Is it in the closed sanctioned list below, or does this change amend that list with a justification?

## Good and bad examples (agents pattern-match on them)

**Adding a tunable**

- Good: "Stall window should be configurable." Add `thresholds.stall_window_sessions` to `constants.json` and `Thresholds` in `models.py`, read it in `reps/trends.py`, reference it in docs with `<!--const thresholds.stall_window_sessions-->3<!--/const-->`. One edit site for the value, the rest derived or checked.
- Bad: `const STALL_WINDOW = 3` in a Svelte file. Bad: a second `dashboard/src/config.ts` "for UI thresholds". Bad: writing "last 3 sessions" in `LOGGING.md` as bare prose.

**Adding a dashboard number**

- Good: "Show weeks since last deload." Add the computation to `reps/`, add the field to a snapshot model, run `gen.py`, render `lift.weeks_since_deload` in Svelte, test the computation in pytest with literal expectations.
- Bad: computing it in a component from `snapshot.sessions`. Bad: adding a `utils.ts` helper that re-derives it "just for this page".

**Adding an enum value**

- Good: add `deferred` to `Verdict` in `vocab.py`, run `gen.py`. The SQL `CHECK`, Pydantic, MCP tool schema, Zod, and doc enum marker all update. The build fails anywhere a `switch` is now non-exhaustive.
- Bad: adding `'deferred'` to the tuple in `progression_set`, to a Zod `z.enum` by hand, and to `LOGGING.md`.

**Adding a color or icon**

- Good: `--warn-soft` in `tokens.css`, referenced via a class or `theme.color('warn-soft')`. New tokens also join the fixed key list in `lib/theme.ts` (canvas reads computed styles once). Icon path added to `icons.ts`.
- Bad: `ctx.strokeStyle = '#e6c400'` in a chart. Bad: pasting an `<svg>` into a page.

**Adding a route**

- Good: add a row to the route table in `routes.ts`; builders and the parser both update; round-trip test covers it.
- Bad: `location.hash = '#/reports/' + encodeURIComponent(x)` in a component.

**Adding a relationship**

- Good: "goals must reference a real exercise." `goals.exercise REFERENCES lift(exercise)`. The procedural check is deleted.
- Bad: `if not c.execute("SELECT ... FROM lift WHERE ...")` in `goal_add` and again in `doctor`.

**Adding a domain rule**

- Good: define "PR" once in `records.py`; the dashboard, the session report, and MCP all read the same result.
- Bad: reimplementing PR logic in TS because the snapshot didn't include the flag. Add the flag to the snapshot instead.

**Adding test data**

- Good: add a scenario to `tests/scenarios.py`; both pytest and Playwright use its generated fixture.
- Bad: pasting a hand-written snapshot JSON into an e2e spec.

**Referencing a tool or file in docs**

- Good: "`session_end` refuses to close while the gate reports items." The doc lint verifies `session_end` exists.
- Bad: documenting a tool's argument list in prose (MCP schemas own it). Bad: mentioning a command that does not exist ("run `split show`").

**Legitimate second mechanism (rare)**

- Good: SQL `GROUP BY` for weekly volume over `sets` calling the shared `e1rm` UDF and `weeks.py` boundaries. A runtime boundary (scale) justifies SQL, and the definitions are still shared.
- Good: a test asserting `pr_flags == [False, True, False]` with the expected list typed out. An independent oracle is the point.
- Bad: "the frontend needs it faster so I duplicated the formula". Speed is solved by emitting the field, not by copying the rule.

## Anti-patterns to reject on sight

- New files named `utils2`, `helpers`, `common`, `misc`, `constants2`, `config` next to existing owners.
- A new JSON/YAML/TS file holding values that belong in `constants.json`.
- Two functions with different names computing the same thing "with a small twist". Extend the owner with a parameter or fix the definition.
- A comment saying "keep in sync with X". That is a T3 fact; turn it into T1 or T2, or delete the duplicate.
- "Temporary" copies. There is no temporary.
- Widening an ESLint/`ssot_check` allowlist without a justification line that cites a sanctioned duplication class.

## Code-level markers

- Every owner module starts with `# SSOT owner: <concept>. Consumers: <how they derive>.` (TS: `// SSOT owner: ...`).
- Every generated file starts with `GENERATED by scripts/gen.py. DO NOT EDIT. Source: <path>.`
- Every allowlist entry in `ssot_check.py` carries `# sanctioned: <class from spec section 5>, <reason>`.

## Testing scope

Tests pin meaning; schemas pin shape; gates pin repeat violations. In order:

1. **Golden tests assert semantics with literal oracles.** A stall test states the series and the verdict, typed out. It never computes the expectation from the function it verifies. Add one when you add or change a domain definition.
2. **Shape is covered once, by validation.** Strict models plus generated schemas already reject missing, extra, and mistyped fields. Do not golden-test every field of a large view; test the fields that carry a decision (PR flags, tags, verdicts, break facts).
3. **A new gate only for a repeated violation.** Positive test (violation fails) plus negative test (clean tree passes). Do not add gates for rules nothing has broken yet; gate count scales with gate tests, and scaffolding tests have diminishing returns.
4. **A deleted check leaves a refusal test.** When an FK or type subsumes a procedural check, the test attempts the violation and expects the refusal, so enforcement is proven moved, not removed.

## Sanctioned duplication (closed list)

Anything not in this list is a violation. Extending the list requires editing this file with a justification, an example, and the mechanism that keeps the copies aligned.

1. **Test oracles.** Tests state expected values as literals and never compute them from the production function they verify.
2. **Generated, committed artifacts** kept current by `gen.py --check` (schemas, Zod, blank snapshot, fixtures, doc markers).
3. **SQL set-based aggregation** calling shared definitions (the `e1rm` UDF, `weeks.py` bucket boundaries), because per-row Python loops do not scale with `sets`.
4. **Doc prose stating intent and rationale** ("why autoreg never trims below MEV"), never values, enumerations, or tool argument lists.
5. **Playwright screenshot baselines and lockfiles.**
6. **The muscle-name seam:** `constants.json` owns the taxonomy, `lift_muscle.muscle` is a plain column validated at write and by `doctor`. A single named seam.
7. **`liftColor` hashing** as the single place lift identity maps to a color (presentation-only, no domain meaning).
9. **MCP call-shape literals** (`SetField`, `WorkoutField` in `reps/mcp/server.py`): field names of MCP call payloads, not domain facts. They mirror tool signatures by construction (changing a signature breaks its own tool); domain vocabularies stay in `reps/vocab.py`.
8. **Gate catalogs and their tests naming banned identifiers** (`scripts/ssot_check.py`, `dashboard/src/__tests__/ssot.test.ts`). Naming a banned pattern to forbid it is enforcement, not a second mechanism: the gate itself fails the build on real drift, and the name cannot drift because it is a string, not a computation. Section 7 verification commands exclude these enforcement files (plus generated artifacts and test fixtures).
